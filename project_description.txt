Actúa como un Arquitecto de Software Senior y Desarrollador Full-Stack. Necesito que me ayudes a construir una Progressive Web App (PWA) de estudio de idiomas (estilo "SmartCards+"), diseñada específicamente para usarse en un iPhone mediante Safari ("Añadir a la pantalla de inicio").

El objetivo principal es que un estudiante de español pueda guardar frases y vocabulario en contexto ("chunks"), evitando registrar frases duplicadas o muy parecidas, y repasarlas usando un algoritmo de repetición espaciada (SRS).

1. Especificaciones del Stack Tecnológico
Backend: Python con FastAPI (por su rapidez, documentación automática con Swagger/OpenAPI y manejo sencillo de endpoints).

Base de Datos: SQLite (para desarrollo local o servidor sencillo) o PostgreSQL / Supabase.

Frontend: React (usando Vite + TypeScript) estructurado como PWA.

UI / Estilos: Tailwind CSS + Shadcn UI (o componentes estilizados con estilo nativo de iOS: bordes redondeados, tipografía limpia, modo oscuro/claro automático).

Iconos: Lucide React (lucide-react).

PWA Support: vite-plugin-pwa para configurar el manifest.json e iconos para iOS.

2. Características Clave del Sistema
Captura Rápida & Comprobación de Duplicados en Tiempo Real:

Al empezar a escribir una frase en español en el campo de texto, el frontend enviará una petición con debouncing (esperar 300ms) al backend para buscar coincidencias exactas o parciales en la base de datos.

Si existe una coincidencia, la app mostrará un aviso visual con la tarjeta existente para evitar crear duplicados.

Estructura de la Tarjeta (Chunking):

Texto Principal (Español): La frase completa.

Traducción (Inglés).

Nota / Contexto (Opcional): Explicación gramatical o situación de uso.

Etiquetas / Tags: Ej. comida, verbo-ir, jerga.

Algoritmo de Repaso Espaciado (SRS):

Implementar una versión simplificada del algoritmo SM-2 o Leitner.

Campos en la BD: next_review_date, interval_days, ease_factor, repetitions.

Botones de respuesta tras ver el reverso: "Otra vez" (Fácil=0), "Difícil" (1), "Bien" (2), "Fácil" (3).

Interfaz Adaptada a iPhone (PWA):

Diseño Mobile-First touch-friendly.

Botones inferiores estilo barra de navegación de iOS (Tab Bar): "Añadir", "Repasar", "Glosario/Buscar".

por que simplificada?

La recomendación de empezar con una versión simplificada responde a razones puramente prácticas de arquitectura y desarrollo de software:

1. Menor complejidad en el Producto Mínimo Viable (MVP)
El algoritmo SM-2 completo (el que utiliza Anki) calcula de forma dinámica múltiples parámetros por cada tarjeta:

Un Factor de Facilidad (Ease Factor) individual que sube o baja según cada respuesta.

Estados de tarjeta: "Nueva", "En aprendizaje", "Repasada" y "Reaprendida" (tras un olvido).

Manejo de lapsos: Un flujo especial para cuando una tarjeta antigua se falla, que la hace volver a pasar por fases de aprendizaje corto (por ejemplo, mostrarla a los 10 minutos y luego al día siguiente).

Fuzzing: Un pequeño ajuste aleatorio en los días para evitar que demasiadas tarjetas coincidan exactamente el mismo día.

Si intentas programar todos estos estados y reglas desde el primer día, la Fase 3 se vuelve desproporcionadamente compleja de escribir y probar.

2. Facilidad de depuración (debugging)
Con una versión simplificada o un Sistema Leitner (basado en niveles o "cajas"):

Solo necesitas guardar en la base de datos el nivel de la tarjeta (por ejemplo, del 1 al 5) y la fecha del próximo repaso.

La lógica en Python es directa:

Acierto: Subes la tarjeta de nivel y le sumas días a la fecha actual (Nivel 1 = +1 día, Nivel 2 = +3 días, Nivel 3 = +7 días, etc.).

Fallo: La devuelves al Nivel 1 y se repasa mañana.

Si algo falla durante las pruebas en el iPhone, es infinitamente más fácil rastrear el error en 10 líneas de código simples que en una máquina de estados completa.

3. Es totalmente escalable (Arquitectura Modular)
Al estar la aplicación bien modularizada, la lógica del repaso estará aislada en una única función de Python en el backend (por ejemplo, calcular_proximo_repaso(tarjeta, respuesta)).

Esto significa que:

Puedes empezar con la versión simplificada para tener la app funcionando, probarla en el iPhone y verificar que el sistema de duplicados y la PWA van fluidos.

Más adelante, cuando quieras hacer el algoritmo más preciso, solo tendrás que sustituir esa función de Python por las fórmulas completas de SM-2 o FSRS, sin necesidad de rehacer la interfaz gráfica ni modificar la estructura de la base de datos.

Para añadir recordatorios diarios programables a tu Web App (PWA) en un iPhone, es importante entender cómo gestiona Apple las notificaciones web.

Desde iOS 16.4, Apple permite que las PWA añadidas a la pantalla de inicio reciban notificaciones push nativas. Sin embargo, a diferencia de una app nativa de App Store, un navegador en iOS no permite programar un "alarma local" interna en segundo plano sin servidor.  

La forma más limpia, fiable y estándar de implementarlo es que tu servidor en Python envíe la notificación Web Push a la hora configurada.  

¿Cómo funciona la arquitectura del recordatorio?
Frontend (React en el iPhone):

En la pantalla de ajustes de la app, tu novia activa la opción "Recordatorio diario" y elige la hora (por ejemplo, 20:00).

El iPhone le pedirá permiso para enviar notificaciones.  

Al aceptar, Safari genera una "suscripción push" (un token único) que el frontend envía al backend en Python.  

Backend (Python / FastAPI):

Guarda en la base de datos la hora elegida y el token del dispositivo.  

Utiliza una librería de tareas programadas en Python como APScheduler (muy ligera y que corre dentro del mismo FastAPI).

Todos los días a la hora fijada, el backend comprueba si tiene tarjetas pendientes de repasar y envía el mensaje de aviso al servidor de notificaciones de Apple (APNs) usando la librería pywebpush.  

Service Worker (sw.js en el iPhone):

Aunque la app esté cerrada, el sistema operativo de Apple recibe el aviso del servidor y el Service Worker muestra la notificación en la pantalla de bloqueo de iOS.
